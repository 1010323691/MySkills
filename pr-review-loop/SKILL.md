# PR 审核闭环

修改方与审核方分离：主 Agent 写代码，独立审核子 Agent 下结论。原因很简单——作者最难看见自己的盲点，而「看起来没问题」的自评正是缺陷溜进主干的常见路径。PR 评论是全部审核上下文的唯一事实源：每轮报告、处理状态和结论都写在 PR 上，任何新会话读完 PR 即可接手。结论用完整 HEAD SHA 绑定，审核之后再有任何提交，旧结论自动失效。

下文 `<S>` 指本技能目录下的 `scripts/pr_state.py`（`python3 <S> …`，Windows 用 `python`），`<R>` 为 `OWNER/REPO`，`<N>` 为 PR 编号，`<remote>` 为第 0 节记录的 remote 名。轮次统一称「第 k 轮审核」，首轮 k=1。

## 流程总览

```text
0 准备+自检 ─→ 1 建/接 PR ─→ 2 独立审核 ──CLEAR──→ 仅供参考留痕 → 5 门禁 → 合并 → 清理 → 最终报告
                          ↑      └─BLOCKED─→ 3 逐项处理 ─→ 发布处理报告 ─┐
                          └──── 复审：续用或新起审核者（2.2；第 4 轮仍 BLOCKED 即升级用户）┘
```

| 角色 | 做 | 不做 |
|---|---|---|
| 主 Agent | 修改、提交前自检、验证、提交推送、建 PR、处理发现项、发布处理报告、启动/续用审核者、合并与清理 | 以自检代替独立审核；单方关闭/延后必须修与建议修；审核期间推送 |
| 审核子 Agent | 按 [references/reviewer-guide.md](references/reviewer-guide.md) 只读审核、按需在隔离目录验证、发布审核报告、核销与裁决 | 改项目代码、提交、推送、合并 |
| 用户 | 授权范围、裁定僵持分歧或延期、执行被宿主拒绝的合并命令 | — |

## 授权边界

- 仅在用户明确要求**执行**本流程时启动。用户只提到技能名、询问用法、要求评审或修改本技能文件，都不构成执行授权——本技能不会因被读取或被评测而扩大权限。
- **一经启动，直接进入第 0 节，不反问用户**：不问「是否开始」「要不要建 PR/合并」「用哪个分支/策略」之类的确认。信息缺失时按本技能给出的取值顺序自行决定（base、分支前缀、合并策略、验证范围等）并在 PR 与最终报告中注明；多 remote、多个候选 PR 等歧义自行核实，核实不了才作为阻塞项报告。只有第 4 节的升级条件、权限/工具缺失（含宿主拒绝合并），以及确需用户裁定的事项才找用户。
- 启动完整闭环即授权本次范围内的提交、推送、建 PR、发布评论、修复、合并和安全清理本轮分支，无需逐步询问。用户限定「只审核」「不要合并」「不推送」「修复后不复审」等时以其为准，走到授权边界即停，并在 PR 上发布「闭环状态」评论（模板见 [references/report-templates.md](references/report-templates.md)）写明缺失门禁与恢复动作；限定模式下门禁不满足就不合并。用户之后明确决定越过门禁时，在 PR 上记录用户原话。
- 未启动闭环时，遵守用户与项目原有的 Git 操作限制。
- 启动审核者时在任务书里明确授权其发布该 PR 的审核评论；审核者不能靠其他 Agent 的回信自行取得权限。

## 宿主适配

| 能力 | 做法 | 兜底 |
|---|---|---|
| 启动审核者 | Claude Code：`Agent` 工具（后台运行，完成自动通知，不要轮询），固定传 `model: "sonnet"`（Sonnet 5.5）、`effort: "medium"`，不随风险分级调整。Codex：子 Agent，用宿主可选模型，强度低风险 `medium`、高风险或拿不准 `high` | 无独立子 Agent 能力时停止并报告缺项，**不以主 Agent 自审代替**。实际配置与上述不符时在最终报告注明 |
| 续用上轮审核者 | Claude Code：同一主会话内用 `SendMessage` 发送续用消息 | 不可用、会话已中断或不满足 2.2 续用条件 → 新起 |
| 合并 | `gh pr merge`（5.3） | 被宿主权限或自动模式分类器拒绝（如 `[Merge Without Review]`）：不重试同一命令，不变通——不直推 base、不 `--admin`、不去掉 SHA 约束、**不用 `gh pr merge --auto` 或宿主 `set_auto_merge` 之类的自动合并替代**。把精确命令交给用户，给两个选项：用户自己执行；或用户在宿主放行该命令后由 Agent 重新执行。完成后本会话继续 5.4 |
| PR 关联 / CI 监控 | Claude Code 桌面版：`mcp__ccd_pr__bind_pr`、`get_status`、`set_monitor`（延迟加载，先用 ToolSearch 加载）；Codex：`attach_artifact` | `python3 <S> --wait-ci`（5.2）；不要假定专用工具存在 |
| 分支前缀 | 宿主设置或用户/项目约定（Codex 惯例 `codex/`） | `review-loop/<kebab-case>` |

宿主提供 CI 监控且已绑定时，以它的事件为准，不再自行轮询。

## 0. 准备

1. 确认在 Git 仓库；读取适用的 `AGENTS.md`/`CLAUDE.md` 与项目验证约定；确认 GitHub 仓库/host、`gh auth status` 权限、子 Agent 能力。缺条件就说明缺项并保留进度。
2. 记录：目标仓库、remote 名、base/head、改动范围、是否已有 PR、完整 HEAD SHA、分支是否本轮创建、**启动时所在分支**（5.4 收尾时回到这里）、用户限制。多 remote 或多个候选 PR 时先核实，不把修改发到猜测的仓库。
3. 检查工作区与 staged diff。只暂存本次范围文件（不用 `git add .`）；用户无关改动原样保留。需切到已有 PR 而工作区不干净时，用独立 worktree（`git worktree add <目录> <分支>`），不自动 stash、丢弃或重置。
4. 风险分级：迁移、认证/额度、并发、路径/子进程、任务分发、CI/权限配置等为高风险，拿不准按高风险。分级决定自检强度（Codex 下还决定审核者强度）。低风险**只是**可能一轮收敛，逐项处置、CI、合并与合并后确认一项不少。
5. **提交前自检（先于验证与建 PR）**：用 `code-review` 技能审自己的改动并修复，把明显缺陷在进入 PR 前消化掉。
   - 范围：待提交的本地改动相对 base 的完整 diff（含未暂存/未提交内容）；接手的已有 PR 则审本轮将新增的提交。
   - 强度：低风险 `medium`，高风险或拿不准 `high`。
   - **只跑一轮**：逐条核对发现项，成立就修，误报留一句理由，写进 PR 正文「自检」小节。修完不复跑；无法当场消化的问题如实列在 PR 正文。用了 `--fix` 时，必须看 `git diff` 逐条核对它落地的改动，误报对应的改动回退并写明理由。
   - **免自检**：改动仅为非行为载体的纯文字（定义见 2.1），或不超过约 20 行且不触及高风险模块时，免自检并在 PR 正文注明。修复轮的标准见第 3 节。
   - `code-review` 不可用时，退化为逐文件通读 diff 自查，并在 PR 正文注明。
   - **自检不等于审核**：不产生 `Verdict`，不满足任何门禁，不减少独立审核——审核者任务书不附自检结论。
6. 按**变更语义**选验证（在自检修复之后跑，证据须对应最终提交内容）：逻辑改动跑受影响测试及项目要求的检查；纯文档/注释/格式用轻量检查并记录不跑全量的理由。配置、权限、workflow、翻译插值、生成文件、提示词/技能文件都可能改变行为，不能凭扩展名或行数判低风险。新 PR 在本地验证通过后才创建；接手的 PR 证据不足时先补验证。因环境原因确实无法完成的验证（需浏览器渲染、外部凭证等）写成「未验证风险」，能在本环境跑的验证不得以此为由省略。
7. **仓库事实一次性核实**：`python3 <S> --repo <R> --repo-facts --base <base>` 读取 base 分支保护（区分「无保护」与「无权限读取」）、rulesets、合并队列、base 上的 workflows、仓库允许的合并方式；head 上的 workflows 看本地工作区。据此：
   - CI 适用性（适用 / 不适用及依据）写进 PR 正文「验证」小节，后续轮次与审核者直接引用，不再重复核实；改动本身新增或修改 workflow 时重新判断。
   - 启用合并队列 → 执行 5.3 **之前**读 [references/merge-queue.md](references/merge-queue.md)。
   - **合并策略**取值顺序：用户指定 → 项目约定（`AGENTS.md`/`CLAUDE.md`，或最近几次合并 PR 的方式）→ 仓库允许的方式按 squash > merge > rebase 优先级取第一个。结果写进 PR 正文。

## 1. 建或接手 PR，启动审核者

**新 PR**：首次提交前切出独立分支（不在默认分支提交）。base 依次取用户指定 → 项目约定 → 核实的远端默认分支，不固定为 `main`。先看 `git log <remote>/<base>..HEAD`：当前分支上已有、但不属于本次范围的提交不能带进 PR——此时从 `<remote>/<base>` 切出新分支，只带入本次改动。提交、推送后创建：

```bash
gh pr create --repo <R> --base <base> --head <head> --title "<中文标题>" --body-file <UTF-8临时文件>
```

正文含修改内容、影响范围、自检（强度、发现数、已修复/反驳要点，或免自检理由）、验证（实际命令、结果、对应 SHA、CI 适用性、未验证风险）、合并策略、已知风险。

**已有 PR**：复用其仓库、base、head、URL，核实提交属于任务范围；不另建重复 PR，不擅自改 base 或强推 head。已合并/关闭或 head 不可写时，先报告状态与可行下一步。已有/共享分支不列入自动删除对象。PR 上已有审核历史时，先按第 4 节「恢复」重建状态。

报告 PR URL，按「宿主适配」关联 PR。然后用 [references/reviewer-brief.md](references/reviewer-brief.md) 的任务书启动本轮审核者。任务书只给事实（PR、SHA、范围、轮次、上轮链接、风险级别、限制、技能路径），**不附主 Agent 对代码质量的判断**——审核者的独立性正来自不被预设结论引导。

审核者运行期间，主 Agent 不修改、不推送该分支。

**CI 与审核并行（每次推送新 HEAD 都适用，首轮与复审相同）**：CI 适用且宿主没有已绑定的 CI 监控时，启动审核者的同时在后台运行 `python3 <S> --repo <R> --pr <N> --wait-ci 30`，并停掉此前尚未结束的等待。它先等检查注册，再等结果；HEAD 变化时自行退出。

## 2. 独立审核

审核者按 reviewer-guide.md 执行，主 Agent 不必通读，但推进依赖以下约定。

### 2.1 结论约定

- 级别：**必须修 / 建议修 / 仅供参考**。必须修、建议修未关闭 → `BLOCKED`；**仅供参考不阻塞 CLEAR，也不阻塞合并**，由主 Agent 决定采纳与否并留痕（第 3 节）。
- **文案类发现一律为仅供参考**：只涉及文字措辞、不改变行为、也不陈述错误事实的指摘（PR 标题/正文/评论、提交信息、代码注释与说明文档的措辞/错别字/排版）。以下属于**行为载体**，其文字问题按实际影响定级：提示词/技能文件（`SKILL.md` 及其 references、`AGENTS.md`/`CLAUDE.md`）、配置、翻译文件与插值、生成文件、被测试或程序断言的运行期字符串、被程序读取的 docstring 与帮助文本、被程序读取的文档。文档中的事实错误（命令、参数、与代码不符的说明）也按实际影响定级。
- 编号 `[P<n>]` 是全 PR 稳定序号，不是严重度。
- 报告末尾两行 `Reviewed-Head: <40 位 SHA>` 与 `Verdict: CLEAR` / `Verdict: BLOCKED（必须修 N 项，建议修 M 项）`；发布后被编辑过的结论，或晚于最新有效结论、格式不符的疑似结论（不论 CLEAR 还是 BLOCKED），`<S>` 都判为阻塞，须由审核者发新的合规报告。
- 审核报告可列「未验证风险」（环境原因无法完成的验证）：不占修复轮次、不阻塞，但必须原样写进最终报告。
- **代发**：审核者无法发布评论时会回信给出报告文件路径与 sha256。主 Agent 校验哈希后**原样**发布（格式见 report-templates.md）。代发只是传输；改动任何内容都使该报告无效。未发布到 PR 的草稿不能作为结论推进。
- 收到回信（评论 URL、结论两行、审核者标识）后，核对 PR 上的评论内容与回信一致；回信缺评论 URL 或结论两行，视为本轮未完成。
- **结论可信条件**（无回信可核对时，如中断恢复）：评论首部写明审核者标识与配置（模型 / 强度 / 新起或续用）；`<S>` 未报告该评论被编辑、其后无格式不符的结论；与前后处理报告的轮次和 SHA 连贯；代发的有 sha256 标注。全部满足可沿用，否则起新审核者对当前 HEAD 复核。GitHub 评论常共用账号，不能只凭作者或搜到 `Verdict: CLEAR` 字样认定。

### 2.2 复审：续用还是新起

续用上轮审核者（`SendMessage`，消息模板见 reviewer-brief.md）可省去冷启动重读，**全部满足才续用**：

1. 同一主会话内，上轮审核者仍可续用；
2. 本轮待复审项只有「已修复，待核销」或待记录的用户裁定，没有待裁决的反驳；
3. 上轮 SHA..当前 SHA 增量 diff 不超过约 50 行变更，且只改动发现项涉及的文件及其对应的测试文件；
4. 无 base 变化、变基或范围扩大；
5. 本轮是第 2 轮审核；或 HEAD 未变、只剩用户裁定待记录（此时轮次不限）。

任一不满足就新起审核者，并在任务书「审核范围」写明新起原因，它决定读取范围：

- **只因有反驳待裁决**（增量满足第 3、4 条）：读最新审核报告的编号项全表、其后的处理报告、增量 diff 与争议项相关代码——裁决需要的是没给出原判的新视角，不是全量重审。
- **因增量大、范围/base 变化、变基或第 3 轮及以后**：审完整 PR diff，外加编号项全表与全部未关闭项——这些情况需要完整的冷启动审视。
- **会话中断后无法续用**：按增量是否满足第 3、4 条，归入上面两种之一。

续用与新起的报告要求相同。在处理报告与最终报告中注明每轮是续用还是新起及原因。

## 3. 主 Agent 逐项处理

每个发现项都要处置并留痕：

| 状态 | 主 Agent 行动 | 关闭条件 |
|---|---|---|
| 待处理 | 分析事实、影响与范围 | — |
| 已修复，待核销 | 落地修改，列提交与验证证据 | 审核者（续用或新起）核实修复有效 |
| 已反驳，待裁决 | 引用原号，写理由与证据 | 新起的审核者明确接受反驳 |
| 用户裁定：不修 / 延后 | 记录用户原话、范围、理由 | 审核者（续用或新起）记录裁定并据此给结论 |
| 已关闭：修复 / 反驳 / 用户裁定 | 引用核销、裁决或裁定记录 | 保留为历史 |
| 仅供参考：已采纳 / 不采纳 | 写采纳的提交，或一句不采纳理由 | 留痕即关闭，无须核销或裁决 |

- **必须修、建议修**：合理即修，不以「以后再改」跳过；误报、无收益或与其他目标冲突的才书面反驳。必须修不得单方延后；审核者降级只改变级别，不关闭问题、不赋予延后权。
- **仅供参考**：主 Agent 自行判断，值得改就改，不采纳写一句理由即可。BLOCKED 轮里的仅供参考项，若要采纳，尽量与阻塞项的修复同一轮落地，避免为它单独多一轮复审；CLEAR 之后采纳代码类仅供参考项必然多一轮复审，收益不足以抵这轮成本时可不采纳并写明理由。审核者后续基于新事实把它升级为建议修/必须修时，按阻塞项处理。
- 反驳被驳回而主 Agent 仍不同意 → 提交用户裁定，等待期间不合并；主 Agent 不能自行宣布反驳成立。
- **任何新提交都使旧 CLEAR 失效**，没有例外：采纳仅供参考（含注释/文档措辞修正）而产生的提交也要复审，通常满足 2.2 续用条件，成本很低。
- **免送审的只有不改 HEAD 的修改**：PR 标题/正文/评论的措辞用 `gh pr edit` 落地，无须复审。
- **修复提交的自检与验证**：修复增量超过约 50 行或引入新文件/新模块时，推送前按第 0 节第 5 步自检（强度按风险）；否则免自检，由复审兜底，在处理报告注明。验证照第 0 节第 6 步。
- 处置后先发布逐项处理报告（模板见 report-templates.md），再按 2.2 续用或新起审核者。报告覆盖历轮所有未关闭项与本轮核销项；主 Agent 写的「已修复」只是待核销声明。
- **快速路径**：首轮 CLEAR 且「发现项：无」→ 直接进第 5 节。CLEAR 只带仅供参考项 → 逐项决定；不采纳或只用 `gh pr edit` 落地时，在 PR 发一条「仅供参考处置记录」评论后直接进第 5 节；采纳需要提交 → 新 HEAD → 按 2.2 复审。

## 4. 循环、升级与恢复

审核 → 逐项处理 → 验证/提交/推送 → 处理报告 → 复审。每轮在报告中记录轮次、SHA 与全部状态，保证可从 PR 记录恢复。

- 第 4 轮审核仍为 BLOCKED，或出现僵持裁决：向用户提交问题、证据、已尝试方案与待裁定事项，得到裁定前不继续循环。
- 工具失败、权限不足、CI 卡住、分支保护阻塞分别报告原因；它们不算审核轮次，也不能通过降低门禁脱困。
- 取得 CLEAR 后继续第 5 节：合并、确认 MERGED、删除本轮分支都由主 Agent 在本会话完成，不能只报告「审核通过」就结束。**唯一例外**是宿主拒绝合并命令（见宿主适配）。外部状态超出当前会话可观察范围时可以交接：在 PR 上发布「闭环状态」评论，写明 HEAD、已满足/缺失门禁和恢复动作；不声称已完成，不自建未授权的定时任务。

**恢复/接手**：运行 `python3 <S> --repo <R> --pr <N> --dump-comments latest`，它给出当前 HEAD、全部结论，以及最新有效结论及其后的评论正文。用最新审核报告的「编号项全表」加其后的处理报告/处置记录重建状态表；全表缺项或与处理报告对不上时，改用 `--dump-comments all` 回读全部历史。然后：

1. 最新结论为绑定当前 HEAD 的 CLEAR → 按 2.1「结论可信条件」核对，满足即进第 5 节，否则新起审核者复核；
2. 最新结论未绑定当前 HEAD，或有待裁决/待核销项 → 新起审核者（中断后无法续用，读取范围按 2.2）；
3. BLOCKED 未处理 → 第 3 节。

## 5. 合并门禁与收尾

### 5.1 门禁：全部满足才合并

先运行 `python3 <S> --repo <R> --pr <N> --strict`（退出码 0 无阻塞、1 有阻塞），再人工核对它列出的「需人工核对」项。

1. 可信的独立审核者已发布 CLEAR，最新适用报告的 `Reviewed-Head` 等于当前完整 HEAD；更新的 BLOCKED 不被旧 CLEAR 覆盖；结论评论未被编辑、格式合规。
2. 所有必须修、建议修已独立核销、接受反驳，或有用户裁定且审核者已记录；无待处理/待核销/待裁决。仅供参考项已逐项留痕（采纳 / 不采纳及理由）。
3. 当前 HEAD 的适用 CI 全部通过，required checks、required reviews、分支保护与 rulesets 满足；或第 0 节已核实 CI 不适用，且脚本未报告与之矛盾的检查/workflow；或适用 CI 未通过经 5.2 核实为计费故障（欠费）豁免。审核评论的 CLEAR 不是 GitHub 正式 approval，仓库要求正式 review 时仍须满足。
4. PR 为 OPEN、非 draft、无冲突、`mergeable`/`mergeStateStatus` 已算出且可合并，在用户授权范围内。不用 `--admin` 绕过保护。

### 5.2 CI 判断与有界等待

- 第 0 节已核实 CI 不适用 → 跳过本节。宿主有 CI 监控就等它的事件。针对当前 HEAD 的并行等待（第 1 节）已结束时，直接用其结果与 `--strict` 输出判断，不重新等待。否则后台运行：

  ```bash
  python3 <S> --repo <R> --pr <N> --wait-ci 30
  ```

  它先等检查注册（宽限 2 分钟），再每 30 秒查一次，检查列表稳定且全部结束才算结束。退出码：0 全部结束且无失败（skipped 仍须核实）；1 有 fail/cancel；3 宽限期内没有检查注册；5 等待期间 HEAD 变化（对新 HEAD 重新等待）；8 到时仍 pending；2 连续读取出错。宽限期之后才注册的检查（第三方状态、链式 workflow）由合并前的 `--strict` 再读一次兜住。总上限取用户/项目约定，未指定默认 30 分钟；到时仍 pending 就记录状态与恢复动作并交接（第 4 节），不无限等待、不反复重跑 CI。
- 没有检查注册（退出码 3）、无权限、未知状态、required checks 缺失 **都不是通过**：用 `gh run list --repo <R> --commit <SHA>` 和 workflow 触发条件核实，只有确认对该改动确实没有适用 CI 和检查要求，才记录「不适用」。
- `skipped`/`neutral` 要对照工作流触发条件和仓库规则核实；本应执行的测试/安全检查被跳过仍然阻塞。
- failure/cancelled 先查日志定位原因：属于本次改动 → 第 3 节修复（新 HEAD 需复审）；疑似偶发 → 有限次重跑并记录；**核实为计费故障**（欠费、额度耗尽、支付/订阅失效等与本次改动无关的账号级原因，表现为失败、取消或一直 pending/未注册）→ 不必等其通过、不反复重跑：记录证据（检查名、状态、日志摘录），写明「CI 门禁因计费故障（欠费）豁免」，直接按 5.3、5.4 合并并清理分支。豁免只覆盖核实为计费原因的失败/未运行检查；同一 HEAD 上其他真实失败、或未完成且与计费无关的适用检查仍阻塞合并。

### 5.3 绑定已审核版本合并

base 启用合并队列时先读 [references/merge-queue.md](references/merge-queue.md) 并完成其「入队前」要求。门禁满足且完整闭环已授权时直接执行，不再询问：

```bash
gh pr merge <N> --repo <R> --match-head-commit <已审核完整SHA> --<第 0 节确定的合并策略>
```

`--match-head-commit` 防止「检查完 HEAD 后有人又推送」的竞态。版本不符就对新 HEAD 重新审核，**不要**改成不带 SHA 约束的合并重试。审核后若改 base、更新分支、解决冲突或变基，也要重核范围/验证并取得新结论。不带 `--delete-branch`（清理要等确认合并后单独做），不默认用 `--auto`。

命令被宿主权限或分类器拒绝 → 按宿主适配交接，不重试、不变通。返回「已加入合并队列」或 PR 上已有自动合并安排 → 按 merge-queue.md 跟踪：入队不等于合并。其他合并失败：保存错误、查询状态、处理原因；不强推、不强合、不换策略绕过门禁。

### 5.4 确认合并后安全清理

```bash
gh pr view <N> --repo <R> --json state,mergedAt,mergeCommit,headRefOid
```

`state` 为 `MERGED` 且有 `mergedAt` 后，主 Agent 在本会话**直接执行**清理，不询问。只清理**本轮创建、专用于此任务、无他人依赖**的分支：

- 远端：确认远端分支 SHA 仍等于已合并的 `headRefOid`，用带租约的删除，分支若已前进会被拒绝而保留：
  `git push <remote> --delete --force-with-lease=refs/heads/<分支>:<headRefOid> <分支>`
- worktree：本轮为 PR 新建的 worktree 先 `git worktree remove <目录>`（有未提交内容会被拒，此时保留）。
- 主 checkout：当前所在分支就是待删分支时，切回第 0 节记录的启动分支（它仍存在且不是待删分支），否则切到 base；切到 base 后 `git pull --ff-only`。切换因未提交改动或目标分支被其他 worktree 占用而失败时，保留分支并报告。当前在其他分支时不切换。最后 `git fetch --prune <remote>`。
- 本地分支：先 `git branch -d <分支>`。squash/rebase 合并或远端分支已删时 `-d` 常因祖先检查被拒——此时核对 `git rev-parse <分支>` 是否**等于**已合并 PR 的 `headRefOid`：相等则 `git branch -D <分支>`；不相等（有未推送/未合并提交）则保留并说明。不做该 SHA 核对就不用 `-D`。
- 仓库自动删除了远端分支：核实并记录即可。
- 已有/共享/长期分支、被其他 worktree 使用的分支、条件不满足的分支一律保留，报告「已合并，清理未完成/保留原因」，不谎称全部完成。

**最终报告**：PR 链接；最终审核 SHA 与结论链接；每轮审核者配置（模型、强度、续用/新起）；逐项处置汇总（含仅供参考的采纳/不采纳）；验证与 CI（或不适用依据、计费故障豁免证据）；未验证风险；实际合并结果（合并提交）；分支清理结果；残留事项。
