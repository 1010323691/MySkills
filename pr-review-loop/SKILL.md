# PR 审核闭环流程

修改方与审核方分离：审核权归审核子 Agent；`Verdict: CLEAR` 是唯一合并入口。职责约束见文末「红线」。

## 适用前提

- **不自动触发**：本流程仅在用户明确要求时执行（点名本 skill，或明确说「走 PR 审核闭环」）；主 Agent 不得因为「代码改动完成且本地验证通过」就自行进入本流程。
- 当前工作目录必须处于 git 仓库追踪下（`git rev-parse --is-inside-work-tree` 返回 `true`）；否则不适用。
- 进入点：代码修改完成且本地基础验证通过后（后端改动跑后端测试套件；涉及前端/共享流程额外跑 typecheck/build，按项目 CLAUDE.md 约定），再建分支/PR 进入流程。本地验证未通过前不建 PR。审核、修复、合并、删分支均为流程内步骤，不等「全部做完」再建 PR。

## 步骤 0：风险分级

- 高风险（DB 迁移、认证/额度、并发逻辑、路径处理与子进程、任务分发逻辑等）→ 完整循环（步骤 1 → 5）。
- 低风险（UI 细节、文案、文档、单文件小改）→ 单次审核：审核一轮，仅当报告无任何发现项时流程直接结束；只要存在任何未处置项（含建议修/仅供参考）就进入步骤 3 → 4 的修复复审循环（该轮结论行即使是 CLEAR 也不结束流程，处置完须取得新 HEAD 上的 CLEAR）。
- 拿不准按高风险处理。

## 步骤 1：创建 PR（主 Agent）

1. 创建独立分支（kebab-case，如 `fix/task-center-dialog-unified-height`），提交改动。
2. `gh pr create --base main --head <分支> --title "<中文标题>"`；PR 标题必须用中文。正文含中文或反引号时写临时文件用 `--body-file` 传入。
3. PR 正文（中文）四部分：修改内容、影响范围、验证结果（实际跑过的测试/类型检查命令及结果）、已知风险。
4. 创建成功后报告 PR URL；执行环境提供 `bind_pr` 等 CI 监控工具时绑定；已绑定时 CI 状态由监控事件驱动，不得自行轮询。
5. 用 Agent 工具启动审核子 Agent，prompt 包含：PR 号与 URL、base/分支、改动范围，及「你是审核子 Agent，按 `pr-review-loop` skill 步骤 2 执行，只审核评论，不修改代码」。

## 步骤 2：审核（审核子 Agent）

审核内容：代码正确性、逻辑、边界情况、回归风险、PR 报告内容真实性。

- 测试执行边界：主 Agent 的 PR 正文或逐项处理报告中已附全量测试通过的验证证据（实际跑过的命令与结果）时，审核子 Agent 不重复跑全量测试——对照 diff 核销验证证据的真实性与覆盖范围即可；仅当报告缺少验证证据，或对证据的真实性/完整性有具体怀疑（如改动跨模块但只跑了部分套件、结果与改动不符）时，审核子 Agent 才自行补跑相应测试。

**跨功能影响检查（必须）**：核查改动是否影响其他功能——梳理改动触及的调用方、共享模块、数据流、配置项与既有测试覆盖，对照 PR 正文「影响范围」声明确认无遗漏的受影响功能；发现未声明的连带影响，按普通发现项标号与分级处理。

报告格式：
- 每条发现带标号：`[P1]`、`[P2]`……
- 三级分级：必须修 / 建议修 / 仅供参考。
- 阻塞规则固定：**必须修与建议修都阻塞 CLEAR**（只要报告存在任何未处置完的必须修/建议修项，结论行必须是 BLOCKED，不得给 CLEAR）；仅供参考不阻塞 CLEAR（但仍须按步骤 3 逐项处置）。
- 报告末尾固定两行格式（按序）：第一行 `Reviewed-Head: <完整 HEAD SHA>`（审核时的 PR HEAD；结论仅对该 HEAD 有效），第二行 `Verdict: CLEAR` 或 `Verdict: BLOCKED（必须修 N 项，建议修 M 项）`（只列报告中实际存在的级别）。

报告用 `gh pr comment <PR号> --body-file <临时文件>` 提交为 PR 评论，成功后删除临时文件。审核子 Agent 只审核评论，不修改代码。

复审（第 2 轮起）做增量审核，基于上轮逐项处理报告的「处理状态」区块，聚焦复核：
- 未修复 / 未反驳项、本轮修复引入的新问题（编新标号）、自上次评审以来的变更（基于 PR 提交记录识别）。
- 上轮处理报告中被主 Agent 单方面关闭的项（既非「已修复」，也未走「已反驳 → 再裁决通过」流程，含被延后/跳过的项）：视为流程违规，恢复原标号（或编新标号）按必须修要求处置。
- 标注「已修复」项做机械核销：对照 diff 核实已真正修掉，不信任处理报告措辞；标注「已反驳」项按步骤 3 反驳流程再裁决。
- 上轮修复提交属纯非逻辑变更（注释、文案、文档、格式）的，不要求主 Agent 重跑全量测试，也不在复审中重跑——以对照 diff 的机械核销加轻量验证（必要时 typecheck/build）为准。
- 每轮复审新起一个审核子 Agent（不续用旧会话）；新审核者必须先通读 PR 全部提交记录与全部评论（含各轮审核报告与逐项处理报告）再开始审核——审核上下文完全由 PR 记录承载，不依赖任何存活会话。

## 步骤 3：修复（主 Agent）

- 上轮报告的每个标号项（必须修、建议修、仅供参考）都必须逐项审视并给出处置，修改提交到同一分支 / 同一 PR：
  - 合理的项 → 落地修复。建议修与仅供参考项默认按合理处理，不得以「非阻塞、代价小、以后再改」为由延后或跳过。
  - 不合理的项（误报、无实际收益、与项目约定冲突）→ 书面反驳：在 PR 评论中引用问题标号，写明理由与证据 → 审核子 Agent 对反驳再裁决 → 仍不一致时升级用户裁定。该反驳流程是跳过任何项的唯一路径，跳过理由必须写入处理报告；主 Agent 不得单方面关闭任何项。
- 必须修项不得以「延后」关闭，除非经审核子 Agent 重新降级，或用户明确裁定允许延期（延后及依据必须写入处理报告）。
- 修改提交后，先向 PR 提交本轮逐项处理报告：报告必须含「处理状态」区块，逐条列出上轮报告每个标号项的状态（`[P1]` 已修复 / 已反驳（附理由与证据）/ 延后（仅限必须修项，须注明审核重新降级或用户裁定依据）），再交复审。
- 修复提交的验证：修改内容含逻辑变更时，按项目 CLAUDE.md 约定重跑对应验证（后端改动跑后端测试套件；涉及前端/共享流程额外 typecheck/build）；**修改内容为纯非逻辑变更（注释、文案、文档、格式、非功能性微调）时，无需重新跑全量测试**——轻量验证即可（涉及前端代码时 typecheck/build，纯注释类可无），并在处理报告中注明未跑全量的理由。

## 步骤 4：循环与升级

- 循环：审核 → 反馈 → 修改 → 提交 → 修改报告 → 复审，直到 `Verdict: CLEAR`。
- 仍有未处置的必须修/建议修项时不得合并 PR。
- 升级出口：连续 3 个「BLOCKED → 修复 → 复审」循环未收敛，或存在僵持裁决项（反驳被驳回且主 Agent 不接受），暂停循环，把僵持项整理成清单提交用户裁定；按裁定结果恢复流程。

## 步骤 5：合并与删分支

### 5.1 合并前检查

`Verdict: CLEAR` 仅对审核时的 HEAD 有效：审核后 PR 出现任何代码变更或新提交，CLEAR 自动失效，须重新复审获得新 CLEAR 方可合并。

允许合并须同时满足全部条件：
1. 审核子 Agent 给出 `Verdict: CLEAR`
2. 已配置 CI 时全部通过；仓库未配置 CI 时此项不适用。
   （已配置 CI 但步骤 1 未绑定监控（工具不可用）时，合并时点用可用工具（如 `gh pr checks`）检查一次 CI 状态，仍不得持续轮询。）
3. 无未处理/未关闭项：所有标号项均已「已修复」或「已反驳且经审核子 Agent 再裁决」，延后项均已经审核重新降级或用户裁定
4. 最近审核报告的 `Reviewed-Head` 行与当前 PR HEAD 一致（`gh pr view <PR号> --json headRefOid` 或等效手段）

### 5.2 合并

用 `gh pr merge` 合并；失败时回退路径见全局约定（CLAUDE.md）。

### 5.3 合并后确认

确认 PR 实际合并成功（`gh pr view <PR号> --json state,mergedAt` 或 ccd_pr get_status）后删除开发分支（本地 + 远程）；任一条件不满足（未获 CLEAR、Reviewed-Head 不一致、合并失败、CI 未通过或存在未处理审核项），禁止删分支。

## 红线（无例外）

- 审核权归审核子 Agent；主 Agent 不得自行判定审核通过，不得绕过复审直接合并。
- 审核子 Agent 不修改代码；主 Agent 不自我验收。
- 每个发现项只有两条正常关闭路径：已修复，或已反驳且经审核子 Agent 再裁决通过；主 Agent 不得单方面把任何标号项「延后」「跳过」或以「非阻塞」为由不处理（必须修项的延后仅有审核重新降级或用户裁定一条例外路径）。
- 审核报告与逐项处理报告均走 `gh pr comment --body-file` 自动评论 PR（全局约定同样适用）。
