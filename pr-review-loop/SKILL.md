# PR 审核闭环

修改方与审核方分离：主 Agent 写代码，独立审核子 Agent 下结论。原因很简单——作者最难看见自己的盲点，而「看起来没问题」的自评正是缺陷溜进主干的常见路径。PR 评论是全部审核上下文的唯一事实源：每轮报告、处理状态和结论都写在 PR 上，任何新会话读完 PR 即可接手。结论用完整 HEAD SHA 绑定，审核之后再有任何提交，旧结论自动失效。

## 流程总览

```text
0 准备+自检 ─→ 1 建/接 PR ─→ 2 独立审核 ──CLEAR──→ 仅供参考留痕 → 5 门禁 → 合并 → 清理 → 最终报告
                          ↑      └─BLOCKED─→ 3 逐项处理 ─→ 发布处理报告 ─┐
                          └──── 复审：续用或新起审核者（2.2；≤3 轮未收敛即升级用户）┘
```

| 角色 | 做 | 不做 |
|---|---|---|
| 主 Agent | 修改、提交前自检修复（`code-review`）、验证、提交推送、建 PR、处理发现项、发布处理报告、启动/续用审核者、合并与清理 | 以自检代替独立审核；单方关闭/延后必须修与建议修；审核期间推送 |
| 审核子 Agent | 按 [references/reviewer-guide.md](references/reviewer-guide.md) 只读审核、按需在隔离目录验证、发布审核报告、核销与裁决 | 改项目代码、提交、推送、合并 |
| 用户 | 授权范围、裁定僵持分歧或延期 | — |

## 授权边界

- 仅在用户明确要求**执行**本流程时启动。用户只提到技能名、询问用法、要求评审或修改本技能文件，都不构成执行授权——本技能不会因被读取或被评测而扩大权限。
- **一经启动，直接进入第 0 节，不反问用户**：不问「是否开始」「要不要建 PR/合并」「用哪个分支/策略」之类的确认。信息缺失时按本技能与项目约定的默认值自行决定（base、分支前缀、合并策略、验证范围等）并在 PR 与最终报告中注明；多 remote、多个候选 PR 等歧义自行核实，核实不了才作为阻塞项报告。只有第 4 节的升级条件（未收敛、僵持裁决）、权限/工具缺失（含宿主拒绝合并），以及确需用户裁定的事项才找用户。
- 启动完整闭环即授权本次范围内的提交、推送、建 PR、发布评论、修复、合并和安全清理本轮分支，无需逐步询问。用户限定「只审核」「不要合并」「不推送」「修复后不复审」等时以其为准，记录限定模式，走到授权边界即停并报告缺了哪道门禁；限定模式下门禁不满足就不合并。
- 未启动闭环时，遵守用户与项目原有的 Git 操作限制。
- 启动审核者时在任务书里明确授权其发布该 PR 的审核评论；审核者不能靠其他 Agent 的回信自行取得权限。

## 宿主适配

| 能力 | 做法 | 兜底 |
|---|---|---|
| 启动审核者 | Claude Code：`Agent` 工具（后台运行，完成自动通知，不要轮询），传 `model: "sonnet"`（Sonnet 5.5）；`effort` 低风险 `medium`、高风险或拿不准 `high`。Codex：子 Agent，无法指定 Sonnet 时用宿主可选模型并按同样规则选强度 | 无独立子 Agent 能力时停止并报告缺项，**不以主 Agent 自审代替**。实际配置与上述不符时在最终报告注明 |
| 续用上轮审核者 | Claude Code：同一主会话内用 `SendMessage` 发送续用消息 | 不可用、会话已中断或不满足 2.2 续用条件 → 新起审核者 |
| 合并 | `gh pr merge`（5.3） | 被宿主权限或自动模式分类器拒绝（如 `[Merge Without Review]`）：不重试同一命令、不变通（不直推 base、不 `--admin`、不改无 SHA 约束的命令），把带 `--match-head-commit` 的精确命令交给用户执行；用户回复后本会话继续 5.4 确认与清理 |
| PR 关联 / CI 监控 | Claude Code 桌面版的 PR 状态/绑定工具；Codex 的 `attach_artifact` | 5.2 有界等待；不要假定专用工具存在 |
| 分支前缀 | 宿主设置或用户/项目约定（Codex 惯例 `codex/`） | `review-loop/<kebab-case>` |

宿主提供 CI 监控且已绑定时，以它的事件为准，不再自行轮询。

## 0. 准备

1. 确认在 Git 仓库；读取适用的 `AGENTS.md`/`CLAUDE.md` 与项目验证约定；确认 GitHub 仓库/host、`gh auth status` 权限、子 Agent 能力。缺条件就说明缺项并保留进度。
2. 记录：目标仓库、**remote 名**（后续推送与删除分支都用它，下文写作 `<remote>`）、base/head、改动范围、是否已有 PR、完整 HEAD SHA、分支是否本轮创建、**启动时所在分支**、用户限制。多 remote 或多个候选 PR 时先核实，不把修改发到猜测的仓库。
3. 检查工作区与 staged diff。只暂存本次范围文件（不用 `git add .`）；用户无关改动原样保留。需切到已有 PR 而工作区不干净时，用独立 worktree（`git worktree add <目录> <分支>`），不自动 stash、丢弃或重置。
4. 风险分级：迁移、认证/额度、并发、路径/子进程、任务分发、CI/权限配置等为高风险，拿不准按高风险。分级决定自检强度与审核者 effort。低风险**只是**可能一轮收敛，逐项处置、CI、合并与合并后确认一项不少。
5. **提交前自检（先于验证与建 PR）**：改完代码先用 `code-review` 技能审自己的改动并修复，把明显缺陷在进入 PR 前消化掉。
   - 范围：待提交的本地改动相对 base 的完整 diff（含未暂存/未提交内容）；接手的已有 PR 则审本轮将新增的提交。
   - 强度：低风险 `medium`，高风险或拿不准 `high` 及以上；可加 `--fix` 直接落地修复。
   - **只跑一轮**：逐条核对发现项，成立就修，误报留一句理由，写进 PR 正文的「自检」小节。修完不复跑；无法当场消化的问题如实列在 PR 正文。
   - `code-review` 不可用时，退化为逐文件通读 diff 自查，并在 PR 正文注明「未使用 code-review 技能」。
   - **自检不等于审核**：不产生 `Verdict`，不满足任何门禁，不减少独立审核——审核者任务书不附自检结论。
6. 按**变更语义**选验证（在自检修复之后跑，证据须对应最终提交内容）：逻辑改动跑受影响测试及项目要求的检查；纯文档/注释/格式用轻量检查并记录不跑全量的理由。配置、权限、workflow、翻译插值、生成文件、提示词/技能文件都可能改变行为，不能凭扩展名或行数判低风险。新 PR 在本地验证通过后才创建；接手的 PR 证据不足时先补验证。
7. **CI 适用性一次性核实**：查 base 与 head 上是否有 `.github/workflows`、base 分支保护是否要求 required checks（`gh api repos/<R>/branches/<base>/protection`，404 = 无保护；无权限读取时记为未知）。结论（适用 / 不适用及依据）写进 PR 正文「验证」小节，后续轮次直接引用，不再重复核实；改动本身新增 workflow 时重新判断。

## 1. 建或接手 PR，启动审核者

**新 PR**：范围确定后、首次提交前切出独立分支（不在默认分支提交）。base 依次取用户指定 → 项目约定 → 核实的远端默认分支，不固定为 `main`。提交、推送后创建：

```bash
gh pr create --repo <OWNER/REPO> --base <base> --head <head> --title "<中文标题>" --body-file <UTF-8临时文件>
```

正文含修改内容、影响范围、自检（强度、发现数、已修复/反驳要点）、验证（实际命令、结果、对应 SHA、CI 适用性）、已知风险。

**已有 PR**：复用其仓库、base、head、URL，核实提交属于任务范围；不另建重复 PR，不擅自改 base 或强推 head。已合并/关闭或 head 不可写时，先报告状态与可行下一步。已有/共享分支不列入自动删除对象。PR 上已有审核历史时，先按第 4 节「恢复」重建状态。

报告 PR URL，按「宿主适配」关联 PR。然后用 [references/reviewer-brief.md](references/reviewer-brief.md) 的任务书启动本轮审核者（模型与强度见宿主适配）。任务书只给事实（PR、SHA、范围、轮次、上轮链接、风险级别、限制、技能路径），**不附主 Agent 对代码质量的判断**——审核者的独立性正来自不被预设结论引导。

审核者运行期间，主 Agent 不修改、不推送该分支；CI 适用时**同时**在后台启动 5.2 的有界等待，让审核与 CI 并行。

## 2. 独立审核

审核者按 [references/reviewer-guide.md](references/reviewer-guide.md) 执行，主 Agent 不必通读，但推进依赖以下约定。

### 2.1 结论约定

- 级别：**必须修 / 建议修 / 仅供参考**。必须修、建议修未关闭 → `BLOCKED`；**仅供参考不阻塞 CLEAR，也不阻塞合并**，由主 Agent 决定采纳与否并留痕（第 3 节）。
- **文案类发现一律为仅供参考**：只涉及文字措辞、不改变行为的指摘（PR 标题/正文/评论、提交信息、代码注释与说明文档的措辞/错别字/排版）。提示词/技能文件、翻译插值、配置、生成文件、被断言的运行期字符串、被程序读取的文档属于行为载体，不算文案类。
- 编号 `[P<n>]` 是全 PR 稳定序号，不是严重度。
- 报告末尾两行 `Reviewed-Head: <40 位 SHA>` 与 `Verdict: CLEAR` / `Verdict: BLOCKED（必须修 N 项，建议修 M 项）`；格式不符或发布后被编辑过的结论，`scripts/pr_state.py` 判为阻塞。
- **代发**：审核者无法发布评论时会回信给出报告文件路径与 sha256。主 Agent 校验哈希后**原样**发布，正文首行加 `> 代发：审核者 <标识> 原始报告，sha256 <值>，未改动`，其余一字不改。代发只是传输；改动任何内容都使该报告无效。未发布到 PR 的草稿不能作为结论推进。
- 收到回信（评论 URL、结论两行、审核者标识）后，核对 PR 上的评论内容与回信一致。GitHub 评论常共用账号，不能只凭作者或搜到 `Verdict: CLEAR` 字样认定独立审核；来源无法核实的历史结论，起新审核者复核。回信缺评论 URL 或结论两行，视为本轮未完成。

### 2.2 复审：续用还是新起

续用上轮审核者（`SendMessage`，消息模板见 reviewer-brief.md）可省去冷启动重读，**全部满足才续用**：

1. 同一主会话内，上轮审核者仍可续用；
2. 本轮待复审项只有「已修复，待核销」，没有待裁决的反驳；
3. 上轮 SHA..当前 SHA 增量 diff 不超过约 50 行变更，且只改动发现项涉及的文件；
4. 无 base 变化、变基或范围扩大；
5. 不是第 3 轮及以后的复审。

任一不满足就新起审核者：裁决反驳需要没给出原判的新视角，大增量、范围变化和久拖未收敛需要完整的冷启动审视。续用与新起的报告要求相同（完整报告、新问题检查、绑定本轮 HEAD）。在处理报告与最终报告中注明每轮是续用还是新起。

## 3. 主 Agent 逐项处理

每个发现项都要处置并留痕：

| 状态 | 主 Agent 行动 | 关闭条件 |
|---|---|---|
| 待处理 | 分析事实、影响与范围 | — |
| 已修复，待核销 | 落地修改，列提交与验证证据 | 审核者（续用或新起）核实修复有效 |
| 已反驳，待裁决 | 引用原号，写理由与证据 | 新起的审核者明确接受反驳 |
| 已关闭：修复 / 反驳 | 引用核销或裁决评论 | 保留为历史 |
| 延后，经用户裁定 | 记录用户原话、范围、理由 | 审核者记录裁定并据此给结论 |
| 仅供参考：已采纳 / 不采纳 | 写采纳的提交，或一句不采纳理由 | 留痕即关闭，无须核销或裁决 |

- **必须修、建议修**：合理即修，不以「以后再改」跳过；误报、无收益或与其他目标冲突的才书面反驳。必须修不得单方延后；审核者降级只改变级别，不关闭问题、不赋予延后权。
- **仅供参考**：主 Agent 自行判断，值得改就改，不采纳写一句理由即可。审核者后续基于新事实把它升级为建议修/必须修时，按阻塞项处理。
- 反驳被驳回而主 Agent 仍不同意 → 提交用户裁定，等待期间不合并；主 Agent 不能自行宣布反驳成立。
- **任何新提交都使旧 CLEAR 失效**，采纳仅供参考而产生的提交也一样（通常满足续用条件，走轻量核销）。唯一例外是下面的文案豁免。
- **文案豁免**（采纳文案类仅供参考项时免再次送审）：
  - PR 标题/正文/评论：用 `gh pr edit`，不改 HEAD，直接豁免。
  - 提交形式的措辞修正，**同时满足**才豁免：① 只改动审核报告为文案类项点名的文件；② diff 只有注释或说明文档的文字变化；③ 改动文件不是行为载体（见 2.1）；④ 提交线性追加在 `Reviewed-Head` 之上（`pr_state.py` 显示 `ahead`）；⑤ 同轮没有其他未关闭项。任一不满足就按常规复审。豁免由 `pr_state.py` 列出的「CLEAR 后改动文件」逐一对照核实，并在处置记录中列出核对结果。
- **修复提交的自检**：推送前按第 0 节第 5 步对本轮新增改动自检；修复 diff 仅为纯文字，或不超过约 20 行且不触及高风险模块时免自检，在处理报告注明。验证照第 0 节第 6 步。
- 处置后先发布逐项处理报告（模板见 [references/report-templates.md](references/report-templates.md)），再按 2.2 续用或新起审核者。报告覆盖历轮所有未关闭项与本轮核销项；主 Agent 写的「已修复」只是待核销声明。
- **快速路径**：首轮 CLEAR 且「发现项：无」→ 直接进第 5 节。CLEAR 只带仅供参考项 → 逐项决定；不采纳或只经文案豁免落地时，在 PR 发一条「仅供参考处置记录」评论（模板见 report-templates.md）后直接进第 5 节；采纳需改代码 → 新 HEAD → 按 2.2 复审。

## 4. 循环、升级与恢复

审核 → 逐项处理 → 验证/提交/推送 → 处理报告 → 复审。每轮在报告中记录轮次、SHA 与全部状态，保证可从 PR 记录恢复。

- 连续 3 轮「BLOCKED → 处理 → 复审」未收敛，或出现僵持裁决：向用户提交问题、证据、已尝试方案与待裁定事项，得到裁定前不继续循环。
- 工具失败、权限不足、CI 卡住、分支保护阻塞分别报告原因；它们不算修复轮次，也不能通过降低门禁脱困。
- 取得 CLEAR 后继续第 5 节：合并、确认 MERGED、删除本轮分支都由主 Agent 在本会话完成，不能只报告「审核通过」就结束。**唯一例外**是宿主拒绝合并命令（见宿主适配）：交出精确命令，用户执行后继续确认与清理。外部状态超出当前会话可观察范围时可以交接：写明 PR URL、HEAD、已满足/缺失门禁和恢复动作；不声称已完成，不自建未授权的定时任务。

**恢复/接手**：运行 `python3 scripts/pr_state.py --repo <R> --pr <N>`（Windows 用 `python`）看当前 HEAD、全部结论及其绑定 SHA、CI 与阻塞项；再读全部评论重建编号项状态表。最新结论不绑定当前 HEAD → 新起审核者对当前 HEAD 复审（中断后无法续用）；有待裁决/待核销项 → 新起审核者；BLOCKED 未处理 → 第 3 节。

## 5. 合并门禁与收尾

### 5.1 门禁：全部满足才合并

先运行 `scripts/pr_state.py` 取机械事实，再人工核对它列出的「需人工核对」项。

1. 可信的独立审核者已发布 CLEAR，最新适用报告的 `Reviewed-Head` 等于当前完整 HEAD；更新的 BLOCKED 不被旧 CLEAR 覆盖；结论评论未被编辑、格式合规。**例外**：CLEAR 后的提交满足第 3 节文案豁免全部条件时，该 CLEAR 仍适用（脚本仍报「未绑定当前 HEAD」，并列出 CLEAR 后改动文件供核对）；合并时 `--match-head-commit` 用当前 HEAD，并在最终报告注明。
2. 所有必须修、建议修已独立核销、接受反驳，或有用户延期裁定且审核者已确认；无待处理/待核销/待裁决。仅供参考项已逐项留痕（采纳 / 不采纳及理由）。
3. 当前 HEAD 的适用 CI 全部通过，required checks、required reviews、分支保护满足；或第 0 节第 7 步已核实不适用，且脚本未报告与之矛盾的检查/workflow。审核评论的 CLEAR 不是 GitHub 正式 approval，仓库要求正式 review 时仍须满足。
4. PR 为 OPEN、非 draft、无冲突、`mergeable`/`mergeStateStatus` 已算出且可合并，在用户授权范围内。合并策略遵循用户/项目配置，不猜测，不用 `--admin` 绕过保护。

### 5.2 CI 判断与有界等待

- 第 0 节已核实 CI 不适用 → 跳过本节。宿主有 CI 监控就等它的事件。否则用有界等待（后台运行，不阻塞与用户沟通）：

  ```bash
  timeout 600 gh pr checks <N> --repo <R> --watch --interval 30
  ```

  退出码 0 全过；8 或 124（`timeout` 到时）为仍 pending；其他为失败或出错。上限取用户/项目约定，未指定默认单会话 10 分钟；超时就记录状态与恢复动作并交接（第 4 节），不无限等待、不反复重跑 CI。
- `no checks reported`、无权限、未知状态、required checks 缺失 **都不是通过**。刚推送时检查可能尚未注册：稍候再查；仍为空就用 `gh run list --repo <R> --commit <SHA>` 和 workflow 触发条件核实。
- `skipped`/`neutral` 要对照工作流触发条件和仓库规则核实；本应执行的测试/安全检查被跳过仍然阻塞。不要从命令退出码直接推断「全部通过」。
- failure/cancelled 先查日志定位原因：属于本次改动 → 第 3 节修复（新 HEAD 需复审）；疑似偶发 → 有限次重跑并记录。

### 5.3 绑定已审核版本合并

门禁满足且完整闭环已授权时直接执行，不再询问：

```bash
gh pr merge <N> --repo <R> --match-head-commit <已审核完整SHA> <仓库允许的合并策略参数>
```

`--match-head-commit` 防止「检查完 HEAD 后有人又推送」的竞态。版本不符就对新 HEAD 重新审核，**不要**改成不带 SHA 约束的合并重试。审核后若改 base、更新分支、解决冲突或变基，也要重核范围/验证并取得新结论。不带 `--delete-branch`（清理要等确认合并后单独做），不默认用 `--auto`。

命令被宿主权限或分类器拒绝 → 按宿主适配交出这条精确命令，不重试、不变通。返回「已加入合并队列」或 PR 上已有自动合并安排时，读 [references/merge-queue.md](references/merge-queue.md)：入队不等于合并，异步合并不保证绑定已审核 SHA。其他合并失败：保存错误、查询状态、处理原因；不强推、不强合、不换策略绕过门禁。

### 5.4 确认合并后安全清理

```bash
gh pr view <N> --repo <R> --json state,mergedAt,mergeCommit,headRefOid
```

`state` 为 `MERGED` 且有 `mergedAt` 后，主 Agent 在本会话**直接执行**清理，不询问。只清理**本轮创建、专用于此任务、无他人依赖**的分支：

- 远端：确认远端分支 SHA 仍等于已合并的 `headRefOid`，用带租约的删除，分支若已前进会被拒绝而保留：
  `git push <remote> --delete --force-with-lease=refs/heads/<分支>:<headRefOid> <分支>`
- worktree：本轮为 PR 新建的 worktree 先 `git worktree remove <目录>`（有未提交内容会被拒，此时保留）。
- 主 checkout：**只有当前所在分支就是待删分支时**才执行 `git switch <base> && git pull --ff-only`；切换因未提交改动或 base 被其他 worktree 占用而失败时，保留分支并报告。当前在其他分支时不切换，只 `git fetch --prune <remote>`。
- 本地分支：先 `git branch -d <分支>`。squash/rebase 合并或远端分支已删时 `-d` 常因祖先检查被拒——此时核对 `git rev-parse <分支>` 是否**等于**已合并 PR 的 `headRefOid`：相等则 `git branch -D <分支>`；不相等（有未推送/未合并提交）则保留并说明。不做该 SHA 核对就不用 `-D`。
- 仓库自动删除了远端分支：核实并记录即可。
- 已有/共享/长期分支、被其他 worktree 使用的分支、条件不满足的分支一律保留，报告「已合并，清理未完成/保留原因」，不谎称全部完成。

**最终报告**：PR 链接；最终审核 SHA 与结论链接；每轮审核者配置（模型、强度、续用/新起）；逐项处置汇总（含仅供参考的采纳/不采纳）；验证与 CI（或不适用依据）；实际合并结果（合并提交）；分支清理结果；残留事项。

## 红线

提交前先自检并修复，但自检不替代独立审核、不自己给结论；必须修与建议修逐项独立关闭，不单方关闭；仅供参考可不采纳但必须留痕；结论绑定 SHA，新提交即失效，文案豁免只限第 3 节列明条件；CI 与仓库保护不跳过、不绕过；合并命令被拒时交出精确命令，不变通；不超出用户授权；启动后不反问用户；未确认实际合并不删分支。任何缺证据的门禁都要说明缺项并留下可恢复进度。
