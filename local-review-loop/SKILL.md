# 本地审核闭环流程（无 PR 介质）

修改方与审核方分离：审核权归审核子 Agent；`Verdict: CLEAR` 是唯一通过/收尾入口。职责约束见文末「红线」。

本流程与 `pr-review-loop` 共用同一套审核协议内核（风险分级、标号与三级分级、逐项处置、反驳再裁决、循环升级、红线），差异仅在**审核介质**：不建分支、不建 PR、不等 CI、不合并。审核产物与审核上下文由本地审核记录文件 `.review/REVIEW.md` 承载，用**被审文件集合的内容哈希基线**锚定结论有效性（对应 `pr-review-loop` 的 `Reviewed-Head`）。

## 适用前提

- **不自动触发**：本流程仅在用户明确要求时执行（点名本 skill，或明确说「走本地审核闭环」）；主 Agent 不得因为「代码改动完成且本地验证通过」就自行进入本流程。
- **不要求处于 git 仓库**：适用于「代码不上 git」或「在 git 仓库但不想/不便开 PR」的场景。若确需走 PR / CI / 合并，改用 `pr-review-loop`。
- 进入点：代码修改完成且本地基础验证通过后（后端改动跑后端测试套件；涉及前端/共享流程额外跑 typecheck/build，按项目 CLAUDE.md 约定）。本地验证未通过前不进入流程。
- 审核记录文件固定为工作区根下的 `.review/REVIEW.md`（不存在则创建）。`.review/` 为过程记录，默认不纳入版本控制，是否入库由项目约定决定。

## 步骤 0：风险分级

- 高风险（DB 迁移、认证/额度、并发逻辑、路径处理与子进程、任务分发逻辑等）→ 完整循环（步骤 1 → 5）。
- 低风险（UI 细节、文案、文档、单文件小改）→ 单次审核：审核一轮，仅当报告无任何发现项时流程直接结束；只要存在任何未处置项（含建议修/仅供参考）就进入步骤 3 → 4 的修复复审循环（该轮结论行即使是 CLEAR 也不结束流程，处置完须取得新基线上的 CLEAR）。
- 拿不准按高风险处理。

## 步骤 1：圈定审核范围并建立基线（主 Agent）

本地审核没有 PR diff 自动圈定边界，主 Agent 须先显式圈定「被审文件清单」作为审核范围（相当于 PR 的 diff 边界）：

1. 明确本次改动/待审的文件清单：由用户指定，或主 Agent 依据本次改动列出；须覆盖全部被改文件，避免漏审。清单即后续所有轮次的审核范围，中途不随意扩缩。
2. 固定基线指纹算法：对清单内每个文件计算 `sha256(文件内容)`，按「文件路径<TAB>sha256」逐行（UTF-8、按路径升序）拼接成一个文本，再对该文本整体取 `sha256`，即**基线指纹**——算法固定，保证各轮重算可复现一致。
3. 在 `.review/REVIEW.md` 写入（或更新）「范围与基线」区块：被审文件清单、各文件哈希、基线指纹、生成时间，以及改动说明四段（修改内容 / 影响范围 / 已跑验证的命令与结果 / 已知风险——对齐 `pr-review-loop` 的 PR 正文）。
4. 用 Agent 工具启动审核子 Agent，prompt 包含：`.review/REVIEW.md` 路径、被审文件清单、改动范围，及「你是审核子 Agent，按 `local-review-loop` skill 步骤 2 执行，只审核评论，不修改代码；把审核报告追加写入 `.review/REVIEW.md`」。

## 步骤 2：审核（审核子 Agent）

审核内容：代码正确性、逻辑、边界情况、回归风险、改动说明（步骤 1 记录）内容真实性。

- 测试执行边界：主 Agent 在 `.review/REVIEW.md` 的「范围与基线」或逐项处理报告中已附全量测试通过的验证证据（实际跑过的命令与结果）时，审核子 Agent 不重复跑全量测试——对照被审文件核销验证证据的真实性与覆盖范围即可；仅当缺少验证证据，或对证据的真实性/完整性有具体怀疑（如改动跨文件但只跑了部分套件、结果与改动不符）时，审核子 Agent 才自行补跑相应测试。

**跨功能影响检查（必须）**：核查改动是否影响其他功能——梳理改动触及的调用方、共享模块、数据流、配置项与既有测试覆盖，对照步骤 1 记录的「影响范围」声明确认无遗漏的受影响功能；发现未声明的连带影响，按普通发现项标号与分级处理。

报告格式：
- 每条发现带标号：`[P1]`、`[P2]`……
- 三级分级：必须修 / 建议修 / 仅供参考。
- 阻塞规则固定：**必须修与建议修都阻塞 CLEAR**（只要报告存在任何未处置完的必须修/建议修项，结论行必须是 BLOCKED，不得给 CLEAR）；仅供参考不阻塞 CLEAR（但仍须按步骤 3 逐项处置）。
- 报告末尾固定两行格式（按序）：第一行 `Reviewed-Baseline: <基线指纹>`（审核时对被审文件集合计算的整体指纹；结论仅对该基线有效），第二行 `Verdict: CLEAR` 或 `Verdict: BLOCKED（必须修 N 项，建议修 M 项）`（只列报告中实际存在的级别）。

报告以「第 N 轮审核报告」为标题**追加写入** `.review/REVIEW.md`，并在返回主 Agent 的消息里给出结论行。审核子 Agent 只审核评论，不修改代码。

复审（第 2 轮起）做增量审核，基于上轮逐项处理报告的「处理状态」区块，聚焦复核：
- 未修复 / 未反驳项、本轮修复引入的新问题（编新标号）、自上次评审以来的变更（比对当前被审文件与上轮「范围与基线」区块记录的各文件哈希，识别内容已变化的文件）。
- 上轮处理报告中被主 Agent 单方面关闭的项（既非「已修复」，也未走「已反驳 → 再裁决通过」流程，含被延后/跳过的项）：视为流程违规，恢复原标号（或编新标号）按必须修要求处置。
- 标注「已修复」项做机械核销：对照被审文件内容核实已真正修掉，不信任处理报告措辞；标注「已反驳」项按步骤 3 反驳流程再裁决。
- 上轮修复属纯非逻辑变更（注释、文案、文档、格式）的，不要求主 Agent 重跑全量测试，也不在复审中重跑——以对照内容的机械核销加轻量验证（必要时 typecheck/build）为准。
- 每轮复审新起一个审核子 Agent（不续用旧会话）；新审核者必须先通读 `.review/REVIEW.md` 全部历史（各轮审核报告与逐项处理报告）再开始审核——审核上下文完全由 `.review/REVIEW.md` 承载，不依赖任何存活会话。

## 步骤 3：修复（主 Agent）

- 上轮报告的每个标号项（必须修、建议修、仅供参考）都必须逐项审视并给出处置，修改落在同一批被审文件内：
  - 合理的项 → 落地修复。建议修与仅供参考项默认按合理处理，不得以「非阻塞、代价小、以后再改」为由延后或跳过。
  - 不合理的项（误报、无实际收益、与项目约定冲突）→ 书面反驳：在 `.review/REVIEW.md` 处理报告中引用问题标号，写明理由与证据 → 审核子 Agent 对反驳再裁决 → 仍不一致时升级用户裁定。该反驳流程是跳过任何项的唯一路径，跳过理由必须写入处理报告；主 Agent 不得单方面关闭任何项。
- 必须修项不得以「延后」关闭，除非经审核子 Agent 重新降级，或用户明确裁定允许延期（延后及依据必须写入处理报告）。
- 修改完成后，先向 `.review/REVIEW.md` 追加写入本轮逐项处理报告：报告必须含「处理状态」区块，逐条列出上轮报告每个标号项的状态（`[P1]` 已修复 / 已反驳（附理由与证据）/ 延后（仅限必须修项，须注明审核重新降级或用户裁定依据）），再交复审。
- 修复后按步骤 1.2 重算被审文件集合的基线指纹并记入处理报告——因为文件内容已变，上轮 `Reviewed-Baseline` 自动失效，正是触发复审的机制。
- 修复的验证：修改含逻辑变更时，按项目 CLAUDE.md 约定重跑对应验证（后端改动跑后端测试套件；涉及前端/共享流程额外 typecheck/build）；**修改为纯非逻辑变更（注释、文案、文档、格式、非功能性微调）时，无需重新跑全量测试**——轻量验证即可（涉及前端代码时 typecheck/build，纯注释类可无），并在处理报告中注明未跑全量的理由。

## 步骤 4：循环与升级

- 循环：审核 → 反馈 → 修改 → 处理报告 → 复审，直到 `Verdict: CLEAR`。
- 仍有未处置的必须修/建议修项时不得收尾。
- 升级出口：连续 3 个「BLOCKED → 修复 → 复审」循环未收敛，或存在僵持裁决项（反驳被驳回且主 Agent 不接受），暂停循环，把僵持项整理成清单提交用户裁定；按裁定结果恢复流程。

## 步骤 5：收尾（无 PR 介质）

### 5.1 收尾前检查

`Verdict: CLEAR` 仅对 `Reviewed-Baseline` 有效：审核后任一被审文件内容变化，CLEAR 自动失效，须重新复审获得新基线上的 CLEAR 方可收尾。

允许收尾须同时满足全部条件：
1. 审核子 Agent 给出 `Verdict: CLEAR`
2. 无未处理/未关闭项：所有标号项均已「已修复」或「已反驳且经审核子 Agent 再裁决」，延后项均已经审核重新降级或用户裁定
3. 最近审核报告的 `Reviewed-Baseline` 与当前被审文件集合指纹一致（按步骤 1.2 重算核对）
4. （若项目另有本地验证门槛，如必须通过某测试/构建）该项已满足；本流程默认不依赖 CI。

### 5.2 收尾

CLEAR 且基线一致时，主 Agent 在 `.review/REVIEW.md` 追加写入最终结论区块：各轮发现项总数与处置汇总、最终 `Verdict`、最终 `Reviewed-Baseline`，流程结束。不建分支、不合并（无 git/PR 介质）；若恰好在 git 仓库且需要版本控制，是否提交由用户/项目约定决定，不在本流程强制。

### 5.3 收尾后确认

任一条件不满足（未获 CLEAR、基线不一致、存在未处理审核项）→ 禁止宣称收尾，回步骤 3/4 继续。

## 红线（无例外）

- 审核权归审核子 Agent；主 Agent 不得自行判定审核通过，不得绕过复审直接收尾。
- 审核子 Agent 不修改代码；主 Agent 不自我验收。
- 每个发现项只有两条正常关闭路径：已修复，或已反驳且经审核子 Agent 再裁决通过；主 Agent 不得单方面把任何标号项「延后」「跳过」或以「非阻塞」为由不处理（必须修项的延后仅有审核重新降级或用户裁定一条例外路径）。
- 审核报告与逐项处理报告均**追加写入**本地审核记录文件 `.review/REVIEW.md`，审核上下文完全由该文件承载，不依赖存活会话。
