# 批准后的实现与验证

## 开工条件

读取简报，核实用户批准了哪一版、哪些页面、哪些技术变化。检查工作区状态与相关项目指引，保留用户未提交修改。批准前不得为了探测兼容性安装依赖或编辑项目。

## 按模式落地

- 新设计：在已批准位置建立界面，优先提取所需布局与组件，配置已选主题；只在范围确实需要时引入相应依赖。没有明确 API 接入范围时标明演示数据和待接入边界。
- 优化：针对痛点修改相关页面，保留约定路由、接口和交互。局部优化谨慎修改全局 token，避免影响未批准页面；需要全局改色时先展示影响范围并确认。
- 重构：保留确认的业务行为，分段替换组件与适配层，避免一边迁移一边偷偷改需求。技术栈 / 认证 / 路由迁移必须在批准范围里。

沿用项目包管理器、锁文件、组件组织和样式机制。上游 `@/` 别名、Providers、useTableUrlState 与 route search 依赖需整体评估；不要只复制 TSX 后补一批未经确认的架构变化。

## 视觉与交互质量

- 使用语义 tokens 表达配色，浅色 / 暗色分别适配前景、背景、边框、焦点、图表与侧栏。
- 表格明确筛选、排序、分页、批量操作及其状态持久化方式；表单明确验证、错误与反馈。
- 实际 API 和模拟数据边界清晰；权限在实际业务层落实，不能仅靠隐藏导航项。
- 保留键盘操作、焦点可见性、标签、弹窗焦点管理和可读对比；状态不能仅靠颜色表达。
- 手机适配导航、筛选与表格溢出，避免缩小整个桌面页来冒充响应式。

## 验证

从目标项目 `package.json` 和文档选择实际存在的检查，不凭上游推定命令。上游核实时有 `build`（tsc -b + vite build）、`lint`、`format:check` 和 Vitest 浏览器测试；这些只是线索，按当前项目为准。

运行与变更相关的构建 / 类型检查及必要 lint、格式检查，行为变化用相关测试或实际流程验证。不要为低影响视觉修改添加只复述实现的测试，也不要对整仓执行格式重写造成无关 diff。

实际打开并查看实现，和批准版本在相同代表视口对比，检查主要任务、空 / 加载 / 失败状态以及要求的主题和设备。审查差异，核对没有超出范围和覆盖用户修改。环境缺依赖或检查失败时说明具体限制，不能声称已通过。

## 交付

展示真实实现截图 / 预览与修改文件，说明解决的痛点、实际运行检查及限制。设计确认不授权发布、改生产数据或连接服务。默认不 git commit、不 git push；需要这些动作时沿用用户明确授权与现有项目规则。
