# movie-magnet-hunt

给一个片单，跨三个资源站批量找磁力，按用户的质量偏好排序，产出可直接导入下载工具的磁力文件。

脚本已把 2026-10-07 实战中踩过的所有坑固化在代码里（Referer、编码、URL 转义、ZBLOG 参数、
base64 磁力等）。**先跑通脚本，再谈手工兜底；手工操作时必须遵守"决策规则"和"禁止事项"。**

## 适用场景

- 用户给出一组电影/剧集名（任何语言混写），要下载链接/磁力，且给出质量偏好（如"1080p 中文字幕优先"）。
- 用户点名 sidhub / 番号楼 / 6V / 6vdyy 等站点。
- 不适用：用户要网盘直链分享页本身、要在线观看、或要 JAV 番号（用 JavBus-GetMagnet）。

## 前置条件（先做一次，全部通过才开工）

1. **用真 Python，别用 `python3`**。Windows 上 `python3` 常是 WindowsApps 商店 stub，会静默失败
   （无输出、退出码 49）。验证：
   ```bash
   python -c "import sys; print(sys.version)"
   ```
   输出版本号才是真解释器。以下所有命令都用 `python`。
2. **三站连通性探测**（各发一个请求即可，全 200 才开工）。把 `<SKILL_DIR>` 换成本技能目录：
   ```bash
   python -c "import sys; sys.path.insert(0, r'<SKILL_DIR>\scripts'); import sites; print('sidhub:', len(sites.sidhub_search('电影')), 'fhl:', len(sites.fhl_search('orange', 1)), '6vw:', len(sites.vw_search('复仇')))"
   ```
   三个数都 >0 才算通。任一为 0：先换词再试一次（站点偶发抽风）；仍失败则该站降级为"不可用"，
   用剩下的站继续，并在结果里注明。
3. **确定输出目录**：在当前会话工作目录下建子文件夹（如 `movie_search/`）。
   **Windows Python 没有 `/tmp`**，一切中间文件用相对路径或该子目录。

## 标准流程

### 第 1 步：片名规范化 + 建关键词表

对每部片子确定：标准中文片名、原语言片名、英文/罗马音名、**年份**、**产地（国家）**、类型（电影/剧集）。
- 年份/产地拿不准时，用 sidhub 搜索结果 cover 上的豆瓣链接（`https://movie.douban.com/subject/<id>/`）核对；
  豆瓣自己的 API（`/j/subject_suggest`）返回 404，**不要依赖它**。
- 每部片子必须尽量给全 `year` 和 `country`——它们是后续同名消歧的唯一可靠依据。

生成片单 JSON（`movies.json`）：

```json
[
  {"no": 1, "cn": "你的婚礼", "year": 2018, "country": "韩国", "type": "movie",
   "keywords": {"sidhub": ["你的婚礼", "On Your Wedding Day", "너의 결혼식"],
                "fhl": ["Your Wedding Day", "On Your Wedding Day"],
                "vw": "你的婚礼"}}
]
```

关键词构造规则（**每个站至少 2 个候选词**，第一个是中文主名，后面是备用）：
- `sidhub`（中文站，模糊匹配标题）：中文片名 → 原语言片名 → 官方英文名，按此顺序。
- `fhl`（**仅 ASCII**，十六进制编码，子串匹配）：英文片名 → 带点英文（`Strobe.Edge`）→ 日文罗马音。
  韩片用官方英文名；**韩文/日文/中文都搜不了**，写非 ASCII 词脚本会直接抛错。
- `vw`（中文模糊搜索）：中文片名，老片可加年份（如"你的婚礼2018"）。

### 第 2 步：跑主流程

```bash
python -X utf8 <skill>/scripts/hunt.py --list movies.json --outdir <输出目录> \
    --per-movie 1 --top 3 --priority subs
```

参数含义：
- `--priority subs`（默认）：字幕优先——没有 1080p 中字时会退到 720p 中字而不是 1080p 日字。
  用户明说"要 1080p，字幕无所谓"时用 `--priority res`。
- `--top N`：每片抓 N 个候选的真实磁力（默认 3，控制请求量）。
- `--per-movie N`：magnets.txt 每片保留几条（默认 1）。
- `--strict`：有片子零磁力时退出码 1。

### 第 3 步：人工复核（不可跳过）

脚本输出三个文件：`资源清单.md`（每片的候选+磁力+来源页+警告）、`magnets.txt`（最终答案）、
`results/<no>.json`（全量数据）。逐个片子做：

1. 看 `results/<no>.json` 的 `warnings`：
   - `year XXXX not in release name` → 打开来源页/对照片名确认没选错片（尤其无年份标注的版本）。
   - `sidhub: not indexed under any keyword` → 正常，sidhub 是**部分索引**，靠其他站的结果即可。
2. 检查最终选择是否真的符合用户要求（如用户要 1080p 中字，但片子只有 720p 中字 → 在交付说明里
   **明确写出降级原因**，不许悄悄交付 720p 说成 1080p）。
3. 字幕语言无法从命名确认时（如裸名 `Ao Haru Ride`），标注"字幕需下载后确认"，不许猜。

### 第 4 步：交付

把 `magnets.txt` 内容（或 `资源清单.md`）发给用户，附：每片的最终选择摘要、降级/存疑说明、
来源站链接（供用户自行核对）。

## 决策规则（强制）

1. **候选排序键**（`--priority subs` 时）：`(年份匹配, 有中字, 分辨率档, 新旧, -大小)`；
   `--priority res` 时：`(年份匹配, 分辨率档, 有中字, 新旧, -大小)`。年份匹配=发布名里没有与期望年份
   冲突的四位年份。**同名不同片（不同年份/国家/动漫）永远排在正确片之后**，这是脚本内置规则。
2. **分辨率判定**：`2160/4K→档3`，`1440/1080→档2`，`1280/720→档1`，`960/864/480/640→档0`。
   片名含 `1280X696` 这种分辨率写法时按第一个命中的档算。4K 视同"满足 1080p 及以上"。
3. **中文字幕判定 token**（命中即算中字）：`中字` `中文字幕` `内封中字` `简繁` `中英双字` `中日双字`
   `CHS` `Chi_Jap` `国语中字` `国语配音` `双语`；`JAPANESE`/`KOREAN`/`日字`/`韩字` 且无上述 token = 原字；
   `无字`/`no-sub` = 0 分。其余 = "未知"（按原字档计分，交付时必须标注）。
4. **sidhub 电影页选择**：搜索返回多个 cover 时，按 `中文名命中×3 + 关键词命中×2 + 产地命中×2 + 年份命中×2`
   排序，最多取前 3 个电影页的资源；页面标题不含目标片名且不含命中关键词的页面整体丢弃。
5. **每部片子最终交付**：恰好 1 条（或用户要求的 N 条）磁力 + 1 句质量说明（如"1080p 中字 8.0G"
   或"无 1080p 中字，720p 中日双字 1.57G"）。
6. **请求预算**：全局 0.3s/请求间隔（sites.py 已内置）；每片 sidhub 电影页 ≤3、磁力详情 ≤3、
   fhl 搜索 ≤2 页×关键词数；12 片左右的全量任务应在几分钟内完成，超过说明请求失控。

## 循环与退出条件

- **关键词回退循环**：某站某关键词 0 结果 → 换下一个关键词（片单里每个站 ≥2 个），全部用完仍 0 →
  记 `not indexed`，换下一站。**禁止**因单关键词 0 结果就宣布该片找不到。
- **磁力抓取循环**：对每个 pick 抓详情页；失败重试 1 次（间隔 1s）仍失败 → 该候选标记
  `magnet_error`，不阻塞其他片子。
- **退出条件**：片单全部处理完 → 写文件 → 汇总行 `done: N movies, M without magnets`。
  `M>0` 时逐片给出"没找到的原因 + 最接近的替代"，`--strict` 下退出码 1。
- **成功标准**（全部满足才算完成）：
  1. 每片要么有 ≥1 条通过 `^magnet:\?xt=urn:btih:[0-9a-f]{40}` 校验的磁力，要么有明确 NOT_FOUND 记录；
  2. 每条磁力都有来源页 URL（sidhub 的 `link_start` 页或 fhl 的 `hash` 页）；
  3. 交付文本里，与用户要求不符之处（降分辨率/无中字/字幕未知/存疑版本）全部显式说明；
  4. `资源清单.md`、`magnets.txt`、`results/*.json` 已写入输出目录。

## 异常处理（症状 → 处置）

| 症状 | 原因 | 处置 |
|---|---|---|
| sidhub 电影页/磁力页 403 | 缺 Referer | `sites.py` 已自动带 `Referer: https://sidhub.cc/`；手工 curl 时必须加，且不能只给 UA |
| `UnicodeEncodeError ... ordinal not in range(128)` | URL query 含中文没转义 | `sites.py` 的 `_fix_url` 已处理；手工拼 URL 时对 query 做 `urllib.parse.quote(q, safe='=&%')` |
| `TypeError: can't concat str to bytes` | `quote_from_bytes()` 在 py3 返回 str | 结果先 `.encode('ascii')` 再拼字节（`sites.py` 已处理） |
| 6vw.cc 搜索"没有搜索到相关的内容"（对任意词） | 参数错：ZBLOG 必须 `show=title,smalltext&tempid=1&tbname=Article`，body 为 **gb18030** | 用 `sites.vw_search()`；注意是 `Article` 不是 `blog` |
| sidhub 搜索 0 cover | sidhub 是**部分索引**，该片没收录 | 换备用关键词 → 仍 0 就用 fhl/vw 的结果；**不要**判定站点故障 |
| 页面中文全是乱码 | 多半是终端 GBK 显示问题，页面本身是合法 UTF-8 | 一律写文件再读，别信终端回显；确属服务端双重编码时只靠 ASCII 部分（片名英文/日期/大小）判断 |
| 控制台 `UnicodeEncodeError` 打印中文 | Windows 控制台 GBK | 命令前加 `-X utf8`（脚本内已 reconfigure stdout） |
| fhl 搜索 0 结果 | 关键词非 ASCII / 该词不在索引 | 检查关键词纯 ASCII；换罗马音、带点、去空格变体；先用 `orange`、`wedding` 这类词验证搜索本身可用 |
| fhl 结果混入大量无关条目 | 子串匹配 + 每页 10 条 | 靠标题相关性/年份过滤；剧集混入用 `type: movie` 自动降权 |
| 6V 文章里只有百度盘链接 | 老帖（2015 年前后）的盘链基本都死 | 只作记录项写入报告，**永远**不作为首选交付 |
| 重跑批量任务结果重复 | 追加写入没去重 | 以 `(片号, 磁力hash)` 去重（`hunt.py` 每片覆盖写 results/<no>.json，天然幂等） |
| 网络瞬断/限流 | 三站都有间歇性抽风 | 单请求失败重试 1 次再记错；整站连续失败则该站降级为"不可用"，其余站继续 |

## 常见陷阱（踩过的，按优先级）

1. **同名不同片**（最危险，交付错片比没交付更糟）
   - 现象：`你的婚礼` 同时命中 2021 大陆版（My.Love.2021）与 2018 韩版（On Your Wedding Day）；
     `青春之旅/Ao Haru Ride` 同时命中 2014 电影与同名动漫（12 话合集）。
   - 根因：三站的搜索都只匹配标题子串，中文短片名极易撞车。
   - 错误做法：拿搜索结果的第一个就用。
   - 正确做法：片单 JSON 里写死 `year` + `country`；脚本用"年份冲突降权 + cover 国家/年份加分"消歧；
     人工复核时看发布名里的年份（如 `.2018.`）与期望一致。
   - 规避：建片单时**强制**填 year/country；拿不准就先用 sidhub cover 的豆瓣链接核实。
2. **`python3` 是 Windows 商店 stub**：无输出、退出码 49，极易误判为"搜索没结果"。
   - 规避：开工前跑前置条件第 1 条；全程用 `python`。
3. **终端 GBK 乱码 → 误诊站点编码 bug**：本次会话曾把 sidhub 误判为"服务端编码坏了"，实际是
   终端显示问题，页面一直是合法 UTF-8。
   - 规避：所有页面内容落文件后用 Read/UTF-8 解码查看；判断页面好坏看 ASCII 结构，不看终端回显。
4. **sidhub 磁力不是直接链接**：电影页列表里是 `/link_start/?seed_id=N` 跳转页，真正的磁力藏在
   页面里的 `const data = "<base64>"`，需 base64 解码。只抓列表页就以为"拿不到磁力"是错的。
5. **fhl 的 flist 不可信**：搜索结果页里每个条目的"文件列表"经常属于相邻的另一个种子。
   - 规避：判断版本只看条目标题 + 详情页磁力的 `dn=`；需要确认字幕语言时去详情页看标题。
6. **发布名年份误标**：YTS/YYeTs 常把 `Kyo Koi O Hajimemasu` 标成 2012（实际 2015）。
   - 规避：年份冲突降权只针对"明显不同的年份"；对 1~3 年内的差异改为人工核对而不是自动丢弃。
7. **6V 的老资源全是死链**：6vdyy 本身搜索是坏的（空库），活跃镜像是 6vw.cc；其 2015 年前后
   的帖子只有百度盘链，10 年后基本失效。
   - 规避：6V 定位是"补充记录"，不占首选位。
8. **豆瓣 suggest API 404**：别在豆瓣上花时间，sidhub 页面里的豆瓣 subject 链接就是现成的标准片名核验。

## 禁止事项

- 禁止在 ≥2 个关键词/站点都没试之前宣布"没找到"。
- 禁止交付未经正则校验的磁力，或没有来源页 URL 的磁力。
- 禁止把 fhl 的 flist、或任何未打开详情页的内容，当作"该种子确定含中文字幕"的证据。
- 禁止把 6V 网盘旧链作为首选交付；禁止谎报做种数、速度、"已确认可下载"。
- 禁止把 720p 交付成 1080p、把"字幕未知"交付成"中字"——不确定就标注不确定。
- 禁止为省步骤把全局 0.3s 请求间隔删掉；禁止单片超过请求预算（≤8 个详情/搜索页）后继续加码。
- 禁止把中间文件写进 `/tmp`（Windows 下不存在）或用户主目录；一律用会话工作目录下的子文件夹。
